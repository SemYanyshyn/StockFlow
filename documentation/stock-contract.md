## Синхронний IStockRepository

Місце: DataAccess; Stock береться тільки з Domain. Точні пропоновані сигнатури:

```csharp
Stock GetForUpdate(int productId, int warehouseId, IDbTransaction transaction);
void Save(Stock stock, IDbTransaction transaction);
IReadOnlyList<Stock> GetAll(int? warehouseId);
```

`IDbTransaction` — System.Data.IDbTransaction. У GetAll параметра транзакції немає.
Методи синхронні; майбутній UI запускає всю довгу сервісну операцію поза UI-потоком,
не розносячи одну транзакцію між незалежними потоками.

GetForUpdate читає наявний рядок із SELECT FOR UPDATE. За відсутності рядка
повертає Stock(ProductId=productId, WarehouseId=warehouseId, Quantity=0,
MinThreshold=0). Save створює рядок через INSERT ... ON CONFLICT DO UPDATE,
передає початковий поріг 0, а в DO UPDATE присвоює **лише quantity**. Редагування
порога іншими операціями не повинно губитися.

GetForUpdate і Save використовують transaction.Connection, не створюють другого
підключення, не закривають передане підключення й не виконують Commit/Rollback.
Сервіс володіє транзакцією та підключенням. GetAll володіє лише своїм окремим
підключенням і повертає матеріалізований список до його Dispose; null означає всі склади.

## Перше надходження і конкуренція: рішення для підтвердження

SELECT FOR UPDATE не блокує відсутній рядок. Якщо дві операції прочитали 0,
обчислили нову кількість і виконали звичайний UPSERT-присвоєння, одна може
перезаписати результат іншої. UNIQUE по парі запобігає дублюванню рядка,
але не втраті кількості.

Пропозиція для очікування SE-9: сервіс відкриває **всю Register-транзакцію** з
IsolationLevel.Serializable. Обидва репозиторії виконуються всередині неї.
При SQLSTATE 40001 сервіс відкочує всю спробу й повертає «Спробуйте ще раз»;
для deadlock 40P01 пропонується така сама відмова поточної спроби. Автоматичного
повтору у фоні немає, бо він змінив би очікування «один успіх, одна відмова».
Наступна явна дія користувача заново відкриває всю транзакцію й повторює читання,
валідацію та записи; повторювати один INSERT усередині відхиленої транзакції не можна.

23505 не замінює 40001: за ним потрібно перевіряти назву constraint. Унікальність
номера руху має окреме повідомлення DuplicateNumberException; конфлікт PK stock
не є дублікатом номера накладної. Необроблений текст провайдера користувачу не показується.

Serializable не означає, що будь-які два запуски обов'язково дадуть конфлікт:
потрібне контрольоване перекриття читань і записів. Якщо операції фактично
послідовні, обидва надходження можуть бути коректними. Для SE-9 обидві спроби
мають прочитати початковий стан до завершення іншої; результат фіксується за фактами.

Правила ізоляції та повтору транзакцій звірено з
[PostgreSQL: Transaction Isolation](https://www.postgresql.org/docs/15/transaction-iso.html),
коди — з [PostgreSQL: Error Codes](https://www.postgresql.org/docs/15/errcodes-appendix.html).
Це обґрунтування пропозиції; SQL на тестовій БД у цьому PR **не запускався**.

## Критерії майбутньої інтеграційної перевірки

1. На окремій тестовій БД зі схемою Мар'яна перевірити: відсутня пара дає Stock=0;
   після Save з'являється рядок із Quantity руху й порогом 0.
2. Для наявного залишку з min_threshold=7 виконати рух і Save: змінюється Quantity,
   поріг лишається 7. Rollback прибирає і рух, і зміну залишку.
3. Контрольовано перекрити дві транзакції списання по 8 зі залишку 10:
   один commit, одна відмова; Quantity=2, один новий рух.
4. Контрольовано перекрити два перші надходження однієї відсутньої пари:
   один commit, другому «Спробуйте ще раз», без втрати кількості й зайвого руху.
5. Записати початковий/кінцевий стан, обидва результати та фактичний SQLSTATE.
   Якщо результат відрізняється, уточнити механізм/погодження, не підганяти звіт.

Ці перевірки **ще не виконано**; fake Rollback у сервісному тесті не є доказом
атомарності PostgreSQL. SE-1 не позначається Done до підтвердження Саші.
